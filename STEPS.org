* Project at a Glance

Python/ipywidgets notebook that sends MIDI sysex to a Yamaha Motif to change
tuning and program. Two independent send streams (tuning, voice) controlled by
a cue list. No audio output — purely a controller. The notebook runs on macOS
alongside Logic Pro; Logic handles playback, this handles tuning/timbre.

* Open Bug: Widget Callbacks

** Symptom

After clicking Advance Both / Adv Tuning / Adv Voice / Reset in the running
widget, the tuning and voice name labels may not visually update. The ARM
button appears to update correctly.

** Where to look

| File      | Location       | What                                      |
|-----------+----------------+-------------------------------------------|
| ui.py     | line 182       | ~state._on_change = refresh~ (direct attr) |
| ui.py     | lines 191–194  | advance/reset lambdas                     |
| state.py  | ~_notify()~    | calls ~self._on_change()~                 |
| state.py  | ~__init__~     | ~_on_change~ default is ~lambda: None~    |

The advance button lambdas (~lambda _: state.advance_both()~) rely on the
chain: button → state method → ~_notify()~ → ~_on_change()~ → ~refresh()~.
The hook is set by direct attribute assignment in ~build_ui~, not via the
constructor's ~on_change~ parameter.

** Most likely causes

1. *Cell run order*: if the kernel is restarted and cell 2 is not re-run,
   ~state._on_change~ reverts to ~lambda: None~. The widget may still display
   (from the previous kernel) but callbacks do nothing.

2. *Background thread*: ~AutoStepper~ calls ~state.advance_*()~ on a daemon
   thread, which calls ~refresh()~ from a non-main thread. In some Jupyter
   environments this silently drops display updates.

3. *ipywidgets version*: behaviour differs between 7.x and 8.x. Check with
   ~python3 -c "import ipywidgets; print(ipywidgets.__version__)"~.

** Debugging steps

#+begin_src python
# Step 1: confirm the hook is wired (run in a scratch cell after cell 2)
print(type(state._on_change))   # should NOT be <lambda>; should be 'function'
print(state._on_change.__qualname__)  # should contain 'build_ui.<locals>.refresh'
#+end_src

#+begin_src python
# Step 2: force a manual refresh to confirm display can update
state._on_change()
#+end_src

#+begin_src python
# Step 3: isolate thread issue — temporarily replace AutoStepper with a no-op
# Comment out these two lines in build_ui() and re-run cell 2:
#   auto_t = AutoStepper(state, interval_s=10.0, mode="tuning")
#   auto_v = AutoStepper(state, interval_s=10.0, mode="voice")
# If advance buttons work after this, the bug is thread-related.
#+end_src

** Likely fix

Pass the callback through the constructor rather than setting it after:
#+begin_src python
# In the main widget cell, replace:
state = PerformanceState(cues=cues, catalog=catalog, midi_out=midi_out)
widget = build_ui(state, midi_out)

# With a pattern where build_ui passes the callback at construction time:
# (requires build_ui to return refresh alongside the widget, or a two-step init)
#+end_src

The cleaner fix is to have ~build_ui~ accept a partially-constructed state and
wire ~on_change~ through the constructor. This is a one-session refactor.
